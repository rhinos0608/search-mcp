# V5.3.0 — Agent-Native Deep Research

**Status**: Planning  
**Source**: Cross-comparison with [local-deep-research](https://github.com/LearningCircuit/local-deep-research) (LDR)  
**Key insight**: LDR's 30+ strategy architecture proves that "let the LLM decide" is fundamentally more flexible than "run this fixed pipeline." Our deep research should default to agent-driven tool-calling, with the existing pipeline as a deterministic fallback for users without LLM access.

---

## Problem Statement

Our current deep research is a **fixed 7-phase pipeline**: decomposition → discovery → extraction → gap analysis → audit → synthesis. This approach:

1. **Cannot adapt tactics mid-research** — the LLM can't decide "I need to read that page" or "I should search PubMed instead of general web"
2. **Has one code path for all queries** — whether the user asks "what is the GDP of France" or "compare quantum computing approaches across arXiv papers from 2023-2024," the same pipeline runs
3. **Uses LLM only for planning/synthesis** — extraction is rule-based, discovery is algorithmic, gap filling is mechanical
4. **Doesn't match the SOTA** — LDR, GPT Researcher, and every serious research agent use tool-calling loops where the LLM drives decisions at every step

### The LDR Lesson

LDR has 30+ strategies, but the ones users actually choose are:

| Strategy | LDR Name | What It Does |
|---|---|---|
| **Agent** | `langgraph-agent` | LLM with tools (search, fetch, subagent spawn). Most flexible. |
| **ReAct Agent** | `mcp` | Custom THOUGHT/ACTION/OBSERVATION loop. No framework dependency. |
| **Pipeline** | `source-based` | Fixed decomposition → search → extract pipeline. Deterministic fallback. |

The agent strategies dominate because they adapt. A query about medical research automatically uses PubMed. A query about current events automatically browses news. The pipeline can't do this without explicit per-query configuration.

## Architecture Shift

### Current

```
deep_research(start) → jobManager.spawn() → orchestrator.run()
                                                  ↓
                                    7-phase fixed pipeline
                                    (decompose → discover → extract → gap → audit → synthesize)
                                                  ↓
                                    WorkerAgent (plans once, executes, synthesizes)
```

### Proposed

```
deep_research(start, strategy?) → jobManager.spawn() → orchestrator.run()
                                                              ↓
                                        StrategyRegistry.select(strategy)
                                         ↙                        ↘
                              AgentStrategy (DEFAULT)        PipelineStrategy (FALLBACK)
                              ┌─ ReAct loop ─────────┐       ┌─ 7-phase pipeline ──┐
                              │ LLM decides:          │       │ Rule-based decompose │
                              │ • search_web(query)    │       │ Algorithmic discover │
                              │ • search_arxiv(query)  │       │ Regex extraction     │
                              │ • fetch_page(url)      │       │ Coverage gap detect  │
                              │ • fetch_focus(url,focus)│      │ Rule-based audit     │
                              │ • research_subtopic()  │       │ Rule-based synthesis │
                              │ • ANSWER               │       └─────────────────────┘
                              └────────────────────────┘       (no LLM required)
                              (requires LLM)
```

### Strategy Selection Matrix

| Scenario | Strategy | Needs LLM? |
|---|---|---|
| Default (LLM configured) | `agent` | Yes |
| Default (no LLM) | `pipeline` | No |
| Tree/broad exploration | `tree` | Optional (LLM for learning extraction) |
| User explicitly requests | `pipeline` / `agent` / `tree` | Depends |

The `strategy` parameter on `deep_research.start` allows explicit selection. When omitted:
- `DEEP_RESEARCH_MODEL` set → `agent`
- No LLM config → `pipeline`
- `depth: "tree"` → `tree` (existing behavior preserved)

## Strategy A: AgentStrategy (New Default)

### ReAct Loop

```
System prompt: "You are a research assistant. Today: {date}. 
               You MUST search before answering. Do NOT answer from memory.
               Available tools: {tool_descriptions}
               Research the query and produce a comprehensive report."

while iteration < maxIterations:
  
  response = llm.chat(systemPrompt + history)
  
  if response.type == "answer":
    finalAnswer = response.content
    break
  
  if response.type == "action":
    tool = response.tool          # e.g. "search_web"
    args = response.arguments      # e.g. {query: "quantum computing...", limit: 10}
    
    result = await executeTool(tool, args)
    observation = formatResult(result, citationCollector)
    
    history.push({role: "assistant", action: tool, args})
    history.push({role: "tool", content: observation})
  
  if response.type == "error":
    history.push({role: "system", error: "Invalid format. Use THOUGHT/ACTION/ARGUMENTS."})
  
  iteration++

if !finalAnswer:
  finalAnswer = synthesizeFallback(citationCollector.getAllResults())

// Post-process: citation handler, source formatting
return buildResult(finalAnswer, citationCollector)
```

### Response Parsing

The LLM responds in a structured format:

```
THOUGHT: I need to understand the basics first before diving deeper.
ACTION: search_web
ARGUMENTS: {"query": "quantum computing fundamentals", "limit": 10}
```

After tool execution:

```
THOUGHT: I have enough information. Let me synthesize.
ANSWER: Quantum computing uses qubits that can exist in superposition...
Sources: [1] IBM Quantum, [2] Nature Physics 2023, ...
```

The parser extracts `THOUGHT`, `ACTION`, `ARGUMENTS` (JSON), or `ANSWER` sections from the LLM response. This is simpler and more reliable than forcing structured JSON output — many local models handle this format better.

|---|---|---|---|

| `search_arxiv` | Free (no key) | `search_arxiv` | Scientific papers from arXiv |
| `search_pubmed` | Free (no key) | `search_pubmed` | Biomedical literature |
| `search_semantic_scholar` | Free (no key) | `search_semantic_scholar` | Academic papers with citations |
| `search_wikipedia` | Free (no key) | `search_wikipedia` | Encyclopedia articles |
| `search_stackexchange` | Free (no key) | `search_stackexchange` | Q&A from Stack Exchange |
| `search_github` | `GITHUB_TOKEN` | `search_github` | Code and repositories |
| `search_hackernews` | Free | `search_hackernews` | Tech news and discussion |
| `search_reddit` | Free | `search_reddit` | Community discussions |
| `fetch_page` | Crawl4AI | `fetch_content` (full) | Full page content |

| `research_subtopic` | LLM | `research_subtopic` | Spawn parallel subagents for complex multi-faceted queries |

Tools are registered dynamically: if `GITHUB_TOKEN` is not configured, `search_github` is omitted from the tool list. The agent never sees tools it can't use.

### `fetch_focus` — The Killer Feature

This is LDR's most impactful efficiency pattern:

```
Agent: fetch_focus(url="https://arxiv.org/abs/2301.12345", 
                    focus="What error correction approach does this paper propose?")
```

The tool:
1. Fetches the page via Crawl4AI (or web_read fallback)
2. If content > 4000 chars, sends to LLM with:
   ```
   Extract ONLY the spans from the page that answer: "What error correction 
   approach does this paper propose?"
   Quote verbatim from the page.
   ```
3. Returns just the relevant excerpts with citation index

This reduces per-page token usage by **60-80%** vs. returning full page content. The agent can call it multiple times with different focus questions against the same URL.

### `research_subtopic` — Parallel Decomposition

When the agent encounters a multi-faceted question, it spawns subagents:

```
Agent: research_subtopic(subtopics=[
  "What is the current state of quantum error correction?",
  "How does surface code compare to cat codes for fault tolerance?",
  "What are the manufacturing challenges for topological qubits?"
])
```

Each subtopic gets its own agent (with its own tool instances for thread safety), runs in parallel (max 4 concurrent), and results are returned in original order. Each subagent inherits the search engines and tools of the parent.

### Configuration

| Setting | Default | Description |
|---|---|---|
| `DEEP_RESEARCH_AGENT_MAX_ITERATIONS` | 30 | Max ReAct loop cycles |
| `DEEP_RESEARCH_AGENT_MAX_SUB_ITERATIONS` | 8 | Max cycles per subagent |
| `DEEP_RESEARCH_AGENT_MAX_SUBTOPICS` | 6 | Max parallel subtopics |
| `DEEP_RESEARCH_AGENT_DEFAULT_FETCH_MODE` | `summary_focus_query` | `full` \| `summary_focus` \| `summary_focus_query` \| `disabled` |
| `DEEP_RESEARCH_STRATEGY` | `agent` (when LLM) | `agent` \| `pipeline` \| `tree` |

### Graceful Degradation

If the agent loop exceeds `maxIterations` without producing an `ANSWER`:
1. Collect all search results from the `CitationCollector`
2. Run a single LLM synthesis: "Synthesize a comprehensive answer from these N sources"
3. If LLM fails, return structured source list as-is

If the LLM call itself fails mid-loop:
1. Retry with exponential backoff (3 attempts)
2. Fall back to collector-based synthesis
3. If all fails, return error with partial results

## Strategy B: PipelineStrategy (Deterministic Fallback)

This is the existing 7-phase pipeline, but **stripped of all LLM dependencies**. It must work with zero LLM calls — pure deterministic algorithms.

### Phase Changes

| Phase | Current | Deterministic Replacement |
|---|---|---|
| 1. Decompose | `llmDecompose()` or rule-based | Rule-based ONLY (keyword extraction from query, pattern matching) |
| 2. Discover | Multi-backend parallel search | Same (no LLM needed) |
| 3. Extract | Rule-based claim extraction (already exists) | Same |
| 4. Gap Analyze | Coverage + confidence analysis | Same (algorithmic, no LLM) |
| 5. Gap Fill | `GapFiller` (uses WorkerAgent) | Skip — gap filling requires LLM for query generation |
| 6. Audit | Rule-based checks (already exists) | Same |
| 7. Synthesize | `ResearchSynthesizer` (rule-based, already exists) | Same |

The key change: the decomposer's `llmDecompose()` path is removed. The rule-based `QueryDecomposer` (which already exists and uses keyword extraction + pattern matching) becomes the ONLY path.

### WorkerAgent Changes

The `WorkerAgent` currently uses LLM for search planning and synthesis. In deterministic mode:
- **Search planning**: Use the sub-question text directly as search queries (no LLM reformulation)
- **Content gathering**: Same as before (algorithmic)
- **Compaction**: Same (algorithmic)
- **Synthesis**: Skip — no LLM means no per-worker synthesis. The final rule-based synthesizer handles everything.

### Result Quality

The deterministic pipeline produces:
- Search results organized by sub-question
- Extracted claims with regex-based confidence
- Coverage metrics per sub-question
- A source-weighted narrative report

It will be less coherent than LLM synthesis but **always works, always free, and never hits rate limits**.

```typescript
function buildAgentTools(config: DeepResearchConfig): AgentTool[] {
  const tools: AgentTool[] = [];
  
  // Always available if any search backend is configured
  if (hasAnySearchBackend(config)) {
    tools.push(createWebSearchTool(config));
  }
  
  // Free, no-key-required tools
  tools.push(createArxivSearchTool());
  tools.push(createPubMedSearchTool());
  tools.push(createWikipediaSearchTool());
  tools.push(createSemanticScholarTool());
  tools.push(createStackExchangeTool());
  tools.push(createHackerNewsTool());
  
  // Conditional tools
  if (config.GITHUB_TOKEN) tools.push(createGithubSearchTool());
  if (config.CRAWL4AI_BASE_URL) tools.push(createFetchPageTool());
  if (config.CRAWL4AI_BASE_URL && config.DEEP_RESEARCH_BASE_URL) {
    tools.push(createFetchFocusTool());  // needs both crawl + LLM
  }
  
  // Subagent research (needs LLM)
  if (config.DEEP_RESEARCH_BASE_URL) {
    tools.push(createResearchSubtopicTool(config));
  }
  
  return tools;
}
```

## Strategy Registry

### Interface

```typescript
// src/research/strategies/types.ts

interface ResearchStrategy {
  /** Unique strategy name (used in user-facing API) */
  readonly name: string;
  
  /** Human-readable description */
  readonly description: string;
  
  /** Whether this strategy requires an LLM */
  readonly requiresLlm: boolean;
  
  /** Run the research for a query */
  analyze(query: string, ctx: StrategyContext): Promise<ResearchResult>;
  
  /** Release resources (called by orchestrator) */
  close?(): Promise<void>;
}

interface StrategyContext {
  state: ResearchStateEngine;
  budget: BudgetTracker;
  llm?: DeepResearchLlmClient;
  config: Required<DeepResearchConfig>;
  abortSignal?: AbortSignal;
  onProgress?: ProgressCallback;
}
```

### Registry

```typescript
// src/research/strategies/registry.ts

class StrategyRegistry {
  private strategies = new Map<string, StrategyFactory>();
  
  register(name: string, factory: StrategyFactory): void {
    this.strategies.set(name, factory);
  }
  
  create(name: string, ctx: StrategyContext): ResearchStrategy {
    const factory = this.strategies.get(name);
    if (!factory) throw new Error(`Unknown strategy: ${name}`);
    return factory(ctx);
  }
  
  selectDefault(ctx: StrategyContext): string {
    // Agent when LLM available, pipeline otherwise
    if (ctx.llm) return 'agent';
    return 'pipeline';
  }
  
  listAvailable(ctx: StrategyContext): StrategyInfo[] {
    return [...this.strategies.entries()]
      .map(([name, factory]) => {
        const s = factory(ctx);
        return { name: s.name, description: s.description, requiresLlm: s.requiresLlm };
      });
  }
}

// Singleton
export const strategyRegistry = new StrategyRegistry();
```

### Registration (at module load time)

```typescript
// src/research/strategies/index.ts

import { strategyRegistry } from './registry.js';
import { AgentStrategy } from './agentStrategy.js';
import { PipelineStrategy } from './pipelineStrategy.js';
import { TreeStrategy } from './treeStrategy.js';

strategyRegistry.register('agent', (ctx) => new AgentStrategy(ctx));
strategyRegistry.register('pipeline', (ctx) => new PipelineStrategy(ctx));  
strategyRegistry.register('tree', (ctx) => new TreeStrategy(ctx));
```

### Orchestrator Changes

```typescript
// src/research/orchestrator.ts

export class ResearchOrchestrator {
  // ... existing fields ...
  private strategy: ResearchStrategy | null = null;

  async run(query: string, depth?: ResearchDepth, ...): Promise<ResearchResult> {
    // ... budget setup, state init, language detection (same as now) ...
    
    const ctx: StrategyContext = {
      state: this.state,
      budget: this.budget,
      llm: this.llm,
      config: this.config,
      abortSignal: this.abortSignal,
      onProgress: this.onProgress,
    };
    
    const strategyName = depth === 'tree' ? 'tree' : strategyRegistry.selectDefault(ctx);
    this.strategy = strategyRegistry.create(strategyName, ctx);
    
    logger.info({ strategy: strategyName }, 'Running research strategy');
    
    const result = await this.strategy.analyze(query, ctx);
    
    // Post-process: compaction, citation, etc. (same as now)
    return result;
  }
  
  async close(): Promise<void> {
    if (this.strategy) await this.strategy.close?.();
  }
}
```

## Confidence & Citation Model

### 3D Confidence (Existing — Enhanced for Agent)

Our existing 3D confidence model applies naturally to agent findings:
- **Evidence confidence**: Source authority (per-source type weighting) + freshness + corroboration count
- **Extraction confidence**: `fetch_focus` = 0.85 (LLM extraction), `fetch_page` = 0.5 (raw page), regex = 0.4
- **Consistency confidence**: Agreement ratio among sources

The agent's findings pass through the same confidence computation as pipeline findings.

### CitationCollector (New)

Thread-safe citation tracking adapted from LDR's `SearchResultsCollector`:

```typescript
// src/research/citationCollector.ts

class CitationCollector {
  private results: SearchResult[] = [];
  private urlIndex = new Map<string, number>(); // url → 1-based citation index
  
  /** Add results, returning the starting citation index for the batch. Thread-safe. */
  addResults(results: SearchResult[], engineName: string): number;
  
  /** Find existing citation index for a URL, or undefined. */
  findCitation(url: string): number | undefined;
  
  /** Get all results for final synthesis. */
  getAllResults(): SearchResult[];
  
  /** Reset per-run state (keeps url index for cross-run dedup). */
  reset(): void;
}
```

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Agent loop diverges / infinite loops | Medium | High | `maxIterations` hard cap (30); recursion depth cap on subagents |
| LLM produces unparseable responses | High | Medium | Regex-based parser with fallback; single synthesis retry on parse failure |
| `fetch_focus` LLM summarization is lossy | Medium | Medium | Always include source URL + citation; agent knows it's summarized, can request full page |
| Deterministic pipeline quality regression | Low | High | Preserve existing rule-based synthesizer; test with golden query dataset |
| Tool discovery overhead per agent cycle | Low | Low | Cache MCP tool discovery; build tools once at strategy init |
| Thread safety of CitationCollector | Medium | High | Use mutex/atomic operations; test with concurrent addResults calls |
| Token budget exhaustion in agent loop | Medium | Medium | Token tracking per iteration; truncate observations >50K chars; hard token cap before fallback |
| Strategy registry added complexity | Low | Medium | Clear default; explicit selection only for power users; backward-compatible API |
