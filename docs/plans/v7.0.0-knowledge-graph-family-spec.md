# V7.0.0 Knowledge Graph Family Consolidation — Specification

> Draft specification for collapsing the current standalone KG tools into a single MCP family.

## Goal

Expose knowledge graph management as one top-level MCP tool, `knowledge_graph`, with actions instead of separate tool registrations.
This keeps the client tool list consistent with the other family tools (`YouTube`, `reddit`, `GitHub`, `packages`, `research`, `browser`).

## Current state

- KG configuration already exists in `src/knowledge/config.ts` and is merged by `src/config.ts`.
- Runtime wiring already resolves `KG_ENABLED` / `KG_DB_PATH` and expands `~` in `dbPath` via `resolveKgDbPath()`.
- The KG capabilities are still exposed as standalone tools:
  - `graph_ingest`
  - `graph_query`
  - `graph_status`
  - `graph_rebuild`
  - `entity_lookup_batch`
  - `family_list`
  - `family_get`
  - `family_merge`
  - `run_list`
  - `run_rollback`
- `src/server.ts` currently registers those tools only when `cfg.knowledgeGraph.enabled` is true.
- `KnowledgeGraphHook` intentionally avoids passive capture for the current `graph_*` / `family_*` / `run_*` / `entity_*` prefixes.

## Proposed public surface

### Family tool

`knowledge_graph`

### Actions

| Action | Current tool | Notes |
| --- | --- | --- |
| `ingest` | `graph_ingest` | Writes KG events from extracted text / URLs |
| `query` | `graph_query` | Read-only KG lookup / search |
| `status` | `graph_status` | Health + DB + projection status |
| `rebuild` | `graph_rebuild` | Projection rebuild controls |
| `entity_lookup_batch` | `entity_lookup_batch` | Batched exact entity lookups |
| `family_list` | `family_list` | Family inventory and merge hints |
| `family_get` | `family_get` | Inspect a single family |
| `family_merge` | `family_merge` | Merge two families |
| `run_list` | `run_list` | List KG runs |
| `run_rollback` | `run_rollback` | Roll back a KG run |

## Design rules

1. **One tool, many actions** — the client sees `knowledge_graph` only.
2. **Action-level availability** — `configIssue` decides whether an action is runnable.
3. **No passive self-capture** — KG family actions must not be re-ingested by `KnowledgeGraphHook`.
4. **Compatibility first** — keep temporary shims for old tool names during the migration window.
5. **Config remains explicit** — example config must show the full `knowledgeGraph` block and the DB path.

## Wiring

### Config

- `config.example.json` should include a full `knowledgeGraph` block matching `DEFAULT_KG_CONFIG`.
- `dbPath` should remain `~/.cache/search-mcp/kg/kg.sqlite` by default.
- The path is resolved by `resolveKgDbPath()` before opening the DB.

### Server registration

- `createServer()` should register the `knowledge_graph` family alongside the other families.
- The family should not be hidden behind a top-level `if (cfg.knowledgeGraph.enabled)` gate.
- Instead, each action should return an actionable runtime error when KG is disabled or the DB cannot be opened.
- `status` should stay available as the diagnostic action.

### Passive capture

- Add an explicit opt-out for KG family actions so `registerFamily()` does not call `kgHook.onToolCall()` for them.
- Keep the current prefix-based exclusion during the transition period so old shims remain non-captured.

### Health reporting

- Add a `knowledgeGraphCapabilities(cfg)` report in `src/health.ts`.
- Surface per-action health under `knowledge_graph.*`.
- Treat `status` as the primary diagnostic action; other actions may be `unconfigured` when KG is disabled.

## Migration plan

### Phase 1 — additive

- Add the `knowledge_graph` family.
- Keep the old standalone KG tools as compatibility wrappers.
- Update docs, config example, and health output.

### Phase 2 — client cutover

- Update tests and client assumptions to use `knowledge_graph`.
- Confirm no clients depend on the old tool names.

### Phase 3 — cleanup

- Remove the standalone KG tool registrations.
- Remove temporary alias paths and any prefix-based exclusions that are only there for shims.
- Keep only the family implementation.

## Acceptance criteria

- `createServer()` exposes a single `knowledge_graph` tool for KG management.
- The family actions validate through the merged schema used by `registerFamily()`.
- KG data path wiring remains unchanged and documented in the example config.
- No passive KG self-capture occurs.
- Existing KG behavior is preserved during the compatibility window.

## Open questions

- Should `status` remain available when KG is disabled, or only report an unconfigured error?
- Should compatibility shims remain visible in `health_check`, or be hidden entirely?
- Do we want action names to stay verbatim (`family_list`, `run_rollback`) or be normalized further (`list_families`, `rollback_run`)?
