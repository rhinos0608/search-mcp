# User-Browser Bridge — V5.2.0 ✅

**Status**: Implemented in full. All 4 phases (user-browser auto-connect, profile persistence, stealth health reporting, docs) are complete and merged.

## Problem Statement

Our current browser automation path (CDP stealth via Playwright + rebrowser-playwright + fingerprint masking) fights a perpetual arms race against Cloudflare, DataDome, and other anti-bot vendors. These vendors update heuristics faster than we can patch CDP leaks. The `stealth.ts` module — while thoughtful — requires constant maintenance to stay effective. Industry consensus: **CDP-based stealth alone is a losing strategy for long-tail authenticated sites.**

## Research Findings

### Industry Approaches

| Approach                     | Tools                                                 | Pros                                                               | Cons                                                           |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------- |
| **Managed Browser APIs**     | Browserbase, Browserless, Steel                       | Professional stealth teams; no eng burden                          | Cost; latency; vendor lock-in; data privacy                    |
| **User Browser Connection**  | CDP MCP `--autoConnect`, Playwright MCP `--extension` | Zero stealth needed; real fingerprint; user sessions work natively | User must be present; consent dialog; can't scale autonomously |
| **Self-Managed CDP Stealth** | Our current `stealth.ts` + rebrowser                  | Full control; scales autonomously                                  | Perpetual arms race; will always lag; high eng cost            |

### Key Industry Precedents

1. **Chrome DevTools MCP (Chrome M144+)**: `--autoConnect` flag that connects to the user's running Chrome instance. Chrome shows a permission dialog. The MCP server reuses the user's full browser state (cookies, sessions, extensions, fingerprints). This is Google's official answer to "how should AI agents interact with my browser?"

2. **Playwright MCP Chrome Extension**: Ships a Chrome extension that acts as a bridge. User installs the extension, selects which tab to share, and Playwright MCP connects through that extension. Full access to user's cookies and sessions.

3. **Browserless/Steel**: Both offer "hybrid automation" modes where a CAPTCHA is streamed to a human for solving, then automation resumes. Acknowledges that pure automation can't solve everything.

### The Real Cost of Stealth Maintenance

Our current `stealth.ts` has 3 layers:

- **Layer 1**: Chromium flags (`--disable-blink-features=AutomationControlled`) — effective ~60%
- **Layer 2**: Init script patches (navigator.webdriver, chrome.runtime, canvas/audio noise) — effective ~30%
- **Layer 3**: Rebrowser-playwright (patches `Runtime.enable` CDP leak) — effective ~10%

Missing (and expensive to implement):

- WebGL fingerprint randomization
- Font fingerprint normalization
- TLS/JA3 fingerprint matching
- Behavioral timing (mouse movement, scroll patterns, typing cadence)
- Proxy rotation infrastructure
- CAPTCHA solving (visual, reCAPTCHA, hCaptcha, Turnstile)

Each of these is a standalone engineering project. Cloudflare releases new detection vectors ~monthly.

## Proposed Solution: Multi-Mode Browser Architecture

### Mode 1: User-Browser Bridge (NEW — recommended default for interactive use)

Connect to the user's existing browser via CDP. The user runs Chrome with remote debugging enabled (`--remote-debugging-port=9222`) and the MCP server connects to it. This inherits the user's:

- Authenticated sessions (cookies, localStorage, IndexedDB)
- Real browser fingerprint (WebGL, fonts, canvas, TLS)
- Installed extensions (password managers, ad blockers)
- Human browsing history / trust signals

**Implementation**: Extend existing `cdpEndpoint` path in `BrowserManager.connect()` with discovery and auto-connect.

**Security**: Chrome M144+ permission dialog model. User must explicitly allow connections.

### Mode 2: Profile-Based Persistence (NEW)

Launch Chrome with a persistent user data directory. The user can pre-authenticate to sites, and the MCP server reuses that profile on subsequent launches.

**Implementation**: Already partially implemented (`BROWSER_PROFILE_DIR` env var, `profile` in `BrowserSessionConfig`). Need to add profile selection UI and ensure profiles survive across server restarts.

### Mode 3: Managed Stealth (EXISTING — demoted to fallback)

Keep our current stealth stack for autonomous/scalable use cases. Use it when neither user browser nor profile is available. Accept that it will be partially effective and document limitations transparently.

**Implementation**: Existing `stealth.ts` + `rebrowser` mode. No new work needed, but add health reporting on stealth effectiveness.

### Mode 4: Managed Browser Proxy (FUTURE — out of scope for V5.2.0)

Optionally proxy through Browserless/Steel for production workloads that need both scale and stealth. This is a cost/benefit tradeoff for users who need autonomous high-scale stealth.

## V5.2.0 Implementation Plan

### Phase 1: User-Browser Auto-Connect (3 files)

**Goal**: `browser.session { op: "start", mode: "user" }` connects to user's Chrome.

**Changes**:

1. **`src/browser/browserManager.ts`** — Add `connectToUserBrowser()` method:
   - Probe common CDP ports (9222, 9223, 9229) for an active Chrome instance
   - Discover available targets (tabs) via `http://127.0.0.1:<port>/json`
   - Create CDP connection via `chromium.connectOverCDP()`
   - Use the existing browser context (don't create a new one)
   - Surface available tabs as the session's pages

2. **`src/tools/families/browser.ts`** — Add `mode` and `browserPort` to session schema:
   - `mode: "stealth" | "user" | "profile"` — which browser mode to use
   - `browserPort: number` — CDP port for user mode (default: auto-detect)
   - `profile: string` — profile name for profile mode (already exists)
   - New action `browser.session { op: "discover" }` — list available user browsers

3. **`src/config.ts`** — Add env vars:
   - `BROWSER_MODE` — default mode (`stealth` | `user` | `profile`, default: `user` when interactive)
   - `BROWSER_CDP_PORT` — default CDP port for user mode (default: 9222)
   - `BROWSER_AUTO_CONNECT` — auto-connect to user browser on startup (default: `false`)

### Phase 2: Profile Persistence Improvements (2 files)

**Goal**: Reusable browser profiles that survive server restarts.

**Changes**:

1. **`src/browser/browserManager.ts`** — Profile launch improvements:
   - Use `chromium.launchPersistentContext()` when profile is set (stores everything: cookies, localStorage, extensions, Service Workers)
   - Fall back to `storageState` save/restore for non-persistent contexts
   - Add profile health check (warn if profile is >30 days old — cookies may expire)

2. **`src/browser/session.ts`** — Add profile metadata:
   - Store profile metadata (createdAt, lastUsed, domain list, cookie count)
   - Add `sessionStore.getProfileInfo(name)` to show what a profile contains
   - Add `sessionStore.migrateProfile(name)` for schema upgrades

### Phase 3: Stealth Health Reporting (1 file)

**Goal**: Make stealth effectiveness transparent, not a false promise.

**Changes**:

1. **`src/browser/stealth.ts`** — Add `StealthReport`:
   - `checkNavigatorWebdriver()` — test if `navigator.webdriver` is spoofed
   - `checkChromeRuntime()` — test if `window.chrome.runtime` exists
   - `checkHeadlessDetection()` — known headless detection vectors status
   - `getStealthHealth()` — aggregate report with pass/fail/warn per check
   - Expose via `browser.session { op: "status" }` when in stealth mode
   - Emit warnings at session start when known gaps exist

### Phase 4: Docs and Migration Guide (2 files)

1. **`docs/tools.md`** — Add "Browser Modes" section explaining the three modes and when to use each.
2. **`docs/quickstart.md`** — Update browser setup instructions for user-browser mode as default.

## Design Decisions

### Decision 1: User-Browser Mode is Opt-In, Not Default

**Rationale**: Connecting to a user's browser is a security boundary. Users must explicitly opt in by (a) starting Chrome with `--remote-debugging-port` and (b) setting `BROWSER_MODE=user` or passing `mode: "user"`. We should never auto-connect to a user's browser without explicit intent.

**Mitigation**: Add a `browser.session { op: "discover" }` action that shows what browsers are available to connect to, with clear information about what connecting would expose.

### Decision 2: Keep Stealth Mode Maintained, Not Abandoned

**Rationale**: There are valid use cases for autonomous, headless browsing (e.g., server-side web scraping, CI/CD testing, scheduled jobs). The stealth stack is valuable for those. But we stop treating it as the primary path.

**Mitigation**: Add health reporting so users know exactly what stealth can and cannot do. Make it a conscious tradeoff, not a hidden failure mode.

### Decision 3: Chrome Extension is Out of Scope for V5.2.0

**Rationale**: Building and maintaining a Chrome extension is a significant commitment (manifest v3 compatibility, Chrome Web Store review, auto-updates). The `--remote-debugging-port` approach works today with zero extension overhead. The extension can come in V5.3.0 if demand justifies it.

### Decision 4: No Managed Browser Proxy Yet

**Rationale**: Every managed browser vendor (Browserbase, Browserless, Steel) has its own SDK. Abstracting over them is non-trivial. Users who need managed browsers can use those services directly. We can add a thin integration later if the demand signal is strong.

## Risk Register

| Risk                                           | Likelihood | Impact | Mitigation                                                            |
| ---------------------------------------------- | ---------- | ------ | --------------------------------------------------------------------- |
| CDP port conflicts (port 9222 already in use)  | Medium     | Low    | Auto-detect ports; let user specify                                   |
| User browser tabs expose sensitive data        | High       | High   | Permission dialog; `discover` action first; never auto-connect        |
| `connectOverCDP` fails on some Chrome versions | Low        | Medium | Test matrix across Chrome versions; graceful fallback to stealth mode |
| Profile corruption across Chrome updates       | Low        | Medium | Schema versioning; automatic migration                                |
| Stealth health report gives false confidence   | Medium     | Medium | Label as "advisory only"; don't guarantee bypass                      |
